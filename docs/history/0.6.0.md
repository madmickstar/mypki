## [0.6.0] - 2026-11-01

A **MINOR** release by this file's own definition: `PLAN.md` §6.3, *ignore the blocked extensions, with consent*, is code rather than a
design, and it moved two things an operator can see — `/csr/sign` gained a confirm-form field, `ignore_extensions`, and a request that asks
for nothing is now answered at **200** where 0.5.2 refused it at **403**. That is the file's MINOR test ("backwards-compatible capability:
a new page, a new `MYPKI_*` knob, a new CLI flag, a new profile field") met by its last term rather than its middle two: the new thing is a
field on an existing form. Nothing here has to be re-learned or re-installed for: every 0.5.2 route keeps its address, no certificate profile
moved (`docs/page-map.md` §7), no row of `issued.db` changed shape, **no `MYPKI_*` knob was added or changed**, an existing data directory
opens with no manual step, the root CA on disk is untouched, and a `<config>/mypki.env` written by 0.5.0, 0.5.1 or 0.5.2 is read back
unchanged. What did move is what mypki *copies*: a request's own ignorable extensions can now reach the issued certificate only through a
ticked box, and the half of §3 rule 6 that asks for CA powers — `CA:TRUE`, `keyCertSign`, `crlSign`, NameConstraints, and anything the
classifier does not recognise — still answers **403** exactly as it did. The gate this release was cut against: 704 tests, 2730 statements /
78 missed = 97.14%, `ruff check` clean, `ruff format` "37 files already formatted", `mypy` clean over 17 source files,
`tools/check_version.py` exit 0, and both harnesses **246 pass / 0 fail / 0 warn** at exit 0.

### Added

- **`/csr/sign` asks before it drops anything.** Step 6 answers in two categories instead of one:
  `csr._csr_extension_problems(csr)` returns `(refused, ignorable)`. *Refused* is unchanged — `BasicConstraints CA:TRUE`,
  `KeyUsage keyCertSign`, `KeyUsage crlSign`, NameConstraints, and (new, and load-bearing) any extension the classifier does not
  recognise, named through `type(value).__name__` so an unknown OID cannot slip through unclassified; those still raise
  `CaPrivilegeRequestedError` and answer **403**. *Ignorable* — `BasicConstraints CA:FALSE`, `KeyUsage (<bits>)` including
  `KeyUsage (no usages set)`, SubjectKeyIdentifier, AuthorityKeyIdentifier, `ExtendedKeyUsage (<names>)`, CertificatePolicies,
  CRLDistributionPoints, AuthorityInfoAccess — no longer refuses a request that could be signed. It is disclosed on the confirmation
  panel and dropped from what mypki copies, **only** when the operator ticks a default-OFF box.
- **`CsrDetails.ignored_extensions`** (a `tuple[str, ...]`, empty by default) carries that disclosure out of `csr.py`, plus one INFO log
  line naming the extensions when the tuple is non-empty. Its docstring says what it is: a description of what will not be copied,
  never an edit of the pasted bytes.
- **`app.CONSENT_FIELD = "ignore_extensions"`** with `_consent_given`, `_consent_problem` and `_dropped_extension_fields`. Consent is read
  from the re-parsed staged request (`details.ignored_extensions`) rather than from anything the form claimed, so a POST cannot consent on
  behalf of extensions it does not carry; `_consent_given` requires a value in `{1,true,on,yes}`, because an HTML checkbox that is unticked
  submits nothing and "the field was present" is not consent. An unticked confirm re-renders at **200** naming every extension at stake plus
  *Nothing was signed*, through the existing `_confirm_rejected` path, with the staged request still reachable under the same `?pending=` id.
  A ticked confirm issues, and each dropped extension appears on the issued page in the same diff block as an edited name,
  as `Extension not copied: <name> … set by mypki instead`.
- **`csr_sign.html`** renders a `provenance dropped-extensions` disclosure ("Not copied from your request — mypki sets these itself", one
  `<li><code>name</code></li>` per extension, plus the byte-identity note) and a `<fieldset class="consent">` whose checkbox is unchecked in
  the markup and whose state word reads `off`. Both blocks render only when there is something to disclose, so a CSR mypki generated itself
  shows neither an empty list nor a box with nothing to consent about. No `|safe` was added anywhere in these blocks.
- **`tests/test_consent.py`, 15 tests**, is the flow-level home for this: default-OFF at the HTTP layer, unticked → 200 with everything named
  and nothing signed, ticked → issued with the drops listed, consent derived from the request rather than the form, `CA:TRUE` refused at 403
  *with* `ignore_extensions=true` posted, and two byte-identity checks comparing the staged DER against a deliberately stripped-and-re-signed
  request. Three older benign-KeyUsage tests in `test_csr_validate.py` were rewritten rather than deleted, and `CRLDistributionPoints` moved
  from the refused parametrisation to the ignorable one and is re-asserted as a disclosure.
- **A sixteenth harness section**, `§16 Dropped extensions need consent (page-map §3 rule 6)`, in both scripts: **30 assertions** each, on two
  real openssl-generated CSRs embedded in the scripts as PEM literals (`consent.csr` 1050 B, `privileged.csr` 1070 B, both verified against
  their own signature), so §16 runs anywhere the other fifteen run and needs no openssl at harness time.

### Changed

- **`docs/page-map.md` §3 rule 6 is now two rules** (6 classifies, 8 consents) and the sentence "no extension list appears on this panel" is
  gone: it was true only while rule 6 refused everything but SAN, and the honest way to make it false was to change the rule rather than to
  reword the sentence. §9's one-line summary and §13's ordering sentence follow the same split.
- **`README.md`'s "no `sign` subcommand" rationale** now says what cannot be bypassed after this change: no path reaches a signature that skips
  step A's checks, and no path copies a request's own extensions without a ticked box.
- **The privilege-refusal hint is longer and accurate**: it names the refused extension *and* points at the box for the half of rule 6 that is
  signable ("Extensions that ask for nothing are listed on the confirmation page, and dropped only when you tick the box there.").
- **`tests/test_packaging.py` covers `inspect.html` and `/inspect`.** Both were omissions rather than decisions: `/inspect` shipped in 0.5.0
  rendering that template while this file — whose whole job is catching a template missing from an artifact — named neither, because an explicit
  asset list can only complain about the names it writes down. Adding the route to the GET sweep is the half that would have caught it by
  rendering it.

### Fixed (harness defects found by running §16 against a correct app)

- **A wildcard host is dialled as loopback.** `MYPKI_HOST=0.0.0.0` (or `::`) is what an operator writes to mean "answer on every interface of
  this box", and `config.py` accepts it for exactly that reason — but it is a bind address, not an address anyone can connect to. Both harnesses
  read their base from mypki's own dotenv layers as of 0.5.2, so a saved `0.0.0.0` flowed straight into the reachability gate. MEASURED on Linux,
  `curl http://0.0.0.0:8591/` happens to connect, which hides the defect here; on Windows it resolves through the route table and the harness
  answers *NOTHING WAS CHECKED* from a healthy server — exit 2, the answer this resolver exists to prevent — and an IPv6-preferring client dials
  `::1` against an IPv4-only bind. The report header still spells what the operator's file says (`base resolved from: … (host '0.0.0.0' is what
  mypki binds, not an address to dial: probing '127.0.0.1')`) while only the host the harness dials becomes loopback. An explicit `--base`/`-Base`
  is never rewritten. Reproduced before it was fixed (`MYPKI_HOST=0.0.0.0` written into `<config>/mypki.env`, server honestly on `:8591`) and
  re-run after: both harnesses **246 / 0 / 0** at exit 0 with the wildcard saved, identical to the runs with `127.0.0.1` saved.
- **Three §16 needles/helpers were wrong while the app was right**, and each was fixed in the harness rather than in the app:
  * `only if you tick the box` matched no build's wording — the hint closes "… you tick the box **there**." It failed in both scripts and in
    `test_consent.py`; the assertion was the defect.
  * `issued_serial()`'s `grep -A 15` window: §16's dropped-extension block pushes the serial row 19 lines below `<h2>Issued:`, so a page that
    renders a serial produced an empty read and a FAIL. The window is now bounded by the facts table instead of a line count.
  * `Get-Page` in §16 left its `%{http_code}` text unassigned, printing three bare `200` lines into the log — which shifts every heading line
    number this document records — and `$(Get-Item $x).Length` interpolated a FileInfo ("…/work/consent.csr.Length bytes") instead of a byte
    count. Both are `.ps1`-only, both fixed, both LF-clean.
- **A recorded measurement that was never a measurement:** an earlier session reported "`scripts/smoke_test.ps1` already had 32 CR-bearing lines
  before this change" and `SMOKE_TESTING.md` repeated the file as *LF-only, zero non-ASCII bytes* in the same breath. The byte-level audit says
  neither is true: **0 CR bytes, 0 CRLF pairs, no BOM** in the current file and in the extracted shipped `mypki-0.5.2`, which is what the LF-only
  claim was measuring. The "32" came from the *command*, not the file: `/bin/sh` here is dash, where `$'\r'` is not an ANSI-C quote — dash reads it
  as a literal `$` followed by a quoted `\r`, handing grep the BRE `$r`, which matches the **32** lines containing a literal `$r`. Under bash the same
  command reports **0**, and `grep -c '\r'` reports **1547** because in a basic regex `\r` is simply `r`. The file has **0** CR bytes under every one of
  those readings. What was corrected is the claim, not the file: no line was rewritten. The audit is now a script (`/tmp/hostrepro/audit2.py`) that
  counts bytes, so the next measurement cannot depend on shell quoting.
- **`openssl` spells the bit `cRLSign`, mypki names it `crlSign`.** MEASURED: `openssl req -addext "keyUsage=…,crlSign"` fails with
  `unknown bit string argument` on openssl 3.5.6 while `cRLSign` works; cryptography and page-map use `crlSign`. The §16 fixture is therefore
  generated with openssl's spelling and asserted with mypki's, which is the pair of spellings an operator will meet.
