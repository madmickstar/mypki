## [0.5.2] - 2026-10-31

A **PATCH** release by this file's own definition: two operator-reported observations, both diagnosed to a specific line before any edit
was made — one about what the smoke harnesses assume about a server, one about how wide a box is on one page. Nothing an operator has to
re-learn or re-install for: every 0.5.1 route keeps its address and its form fields, no certificate profile moved, no `MYPKI_*` knob was
added or changed, a 0.5.1 data directory opens with no manual step, the CA on disk is untouched, and a `<config>/mypki.env` written by 0.5.0
or 0.5.1 is read back unchanged. What mypki *does* did not change: `serve` binds exactly what it bound before, `/inspect` parses and reports
exactly as before, and the one thing that changed on screen is the width of a textarea on one page. The harnesses changed more than the app
does — which is the point of them.

### Fixed

- **Proven by reproduction, not by reading:** extracted from `mypki-0.5.1.zip`, both shipped harnesses were run with no `--base`/`-Base`
  against a live server answering on a saved non-default port (`:8571`, written into `<config>/mypki.env` by a real `POST /settings`; and
  `:8583`) and both printed `NOTHING WAS CHECKED: http://127.0.0.1:8443 is not answering` with **exit 2** — the operator's report, reproduced
  byte for byte. The rewritten harnesses, on the same trees and the same servers, resolved `base: http://127.0.0.1:8571` and
  `base: http://127.0.0.1:8583` naming the config file as the layer that won, and both walked **216 pass / 0 fail / 0 warn** at exit 0. A third
  tree with nothing saved resolved `defaults` and reported the same 216, so the fallback arm is exercised too, and an explicit `--base` still
  outranks every layer as before.
- **Both smoke harnesses lost an operator's server the moment the operator changed its port.** `scripts/smoke_test.sh` read its
  base URL from `${BASE:-http://127.0.0.1:8443}` and `scripts/smoke_test.ps1` from *parameter → `$env:BASE` → literal 8443* —
  neither looked at any of the dotenv layers mypki itself reads, so an operator who saved `MYPKI_PORT=8543` on `/settings`
  (which writes `<config>/mypki.env`) and then ran the documented command got `NOTHING WAS CHECKED: http://127.0.0.1:8443 is not
  answering` against a healthy server. Exit 2 is the worst possible answer here: it says *nothing was checked* while looking like
  "the app is broken". Both harnesses now resolve host **and** port in mypki's own order — `--base`/`-Base` → `$BASE`/
  `$env:BASE` → `MYPKI_HOST`/`MYPKI_PORT` in the real environment → `<config-dir>/mypki.env` → `./.env` → `127.0.0.1:8443` —
  which is `settingsfile.env_file_layers()` (`.env` first, `<config>/mypki.env` later, later wins) plus
  `paths.resolve_config_dir` (`MYPKI_CONFIG_DIR`, then `%APPDATA%\mypki`, then `$XDG_CONFIG_HOME/mypki`, then `~/.config/mypki`)
  read from the outside. The single-source rule that `--version` follows (no literal version in either script) now covers the port
  too: the port is **assigned on exactly one line per harness** (`DEFAULT_PORT` in the `.sh` resolver, `$defaultPort` in the `.ps1`), it is
  mypki's own default rather than a copy of one, and every other mention of 8443 in either file is prose. A value that `config.py` would
  reject is not used either — `MYPKI_PORT=abc` or `MYPKI_PORT=0` fails pydantic's `ge=1` at startup, so the harness falls back to the default
  **and says which layer refused to answer**, because guessing quietly while naming the operator's file as the source is how a harness ends up
  testing its own invention. Host and port resolve independently, because `Settings.host` and `Settings.port` are two fields with two defaults.
  The resolved base and **which layer won** are written in the markdown report header only (`base:` plus a new `base resolved from:` line):
  both logs still begin at line 1 with `§1 Home page`, and `SMOKE_TESTING.md` records heading line numbers for both logs, so a preamble naming
  the resolved base would invalidate that record. Measured after the change: fifteen headings at **1 / 9 / 30 / 32 / 36 / 46 / 59 / 62 / 65 / 83 /
  100 / 141 / 175 / 186 / 196** and the summary at **233**, in **both** logs — identical to each other, and moved only by the five assertions §2
  gained (the resolver itself prints nothing).
- **The rule is deliberately expressed twice, in two different languages.** `.sh` reads the layers through its existing python3
  helper (it already shells out to python3 seven times for HTML entity decoding); `.ps1` implements the same precedence in pure
  PowerShell, because its own header promises "everything else stays PowerShell + curl" and its single non-PowerShell exception is
  `[System.Net.WebUtility]::HtmlDecode`. Two implementations of one rule is a drift risk this repo has to accept knowingly rather
  than by accident, so the asymmetry is written down in both headers and the two chains are labelled as mirrors of each other.
- **`/inspect`'s PEM paste box rendered narrower than every other section on its own page.** The form carries
  `class="settings-form stacked"`, and `style.css` caps `form.stacked` at `max-width: 46rem` while the `.settings-form .field`
  width rule reaches only `input` — there was no `textarea` equivalent, and the generic `input, textarea, select` rule supplies
  `max-width: 100%` with no `width`, so a `<textarea rows="14">` fell back to the browser's own default width (~21rem). On every
  other page that box sits between two full-width `.card` sections (`main` spans 78rem) above a 46rem Save button, which is what
  the operator saw. `/inspect` now carries an additional scoped class, `inspect-form`, and the width rules are scoped to it: the
  46rem cap is lifted for that one form and `#pem_paste` gets `width: 100%` with no `max-width`, so the paste box spans the same
  section the cards above it span. The Inspect button follows it, because a full-width field over a half-width button reads as an
  unfinished row. `.settings-form` is **not** widened — `/settings` posts through the same two classes and its fields are inputs,
  not pastes — and `csr_sign.html`'s `csr_pem` and the SAN textareas on `/csr/generate` and `/csr/sign` stay at 46rem, since those
  forms are plain `stacked` and their boxes are requests being signed rather than a reader's scratchpad. `box-sizing: border-box`
  has been global since 0.1.0, so `width: 100%` needs no padding arithmetic.
- **No browser exists on the host these notes were written on**, so this last item is asserted as *the served stylesheet carries the rule*, the
  posture 0.5.0 established for `.pending-saved`. §2 gained five assertions in both harnesses: `form.stacked.inspect-form { max-width: none; }`
  defined once, `form.inspect-form #pem_paste { width: 100%; max-width: none; }` defined once, `form.inspect-form button.save-settings { max-width:
  none; }` defined once, `.settings-form .field textarea` present **zero** times (the guard that keeps a `/inspect` fix from leaking into
  `/settings` — invisible without a browser and plain in the text of the file), and `GET /inspect` carrying
  `class="settings-form stacked inspect-form"` once, because a CSS rule whose class is missing from the markup styles nothing. The compound
  selector outranks `form.stacked` by specificity rather than by file order, so reordering the stylesheet cannot silently undo the fix. Served
  size moved 25845 → **28152 bytes**. What remains unmeasurable is what the page looks like; nothing here claims to have seen it.

### Testing

- **Gate re-run after both fixes:** 672 tests pass, `TOTAL 2700 statements / 84 missing = 96.89%` — identical to 0.5.1's coverage, because neither
  fix touched a Python module. `ruff check src tests scripts tools`, `ruff format --check src tests`, `mypy src` and `tools/check_version.py` all
  exit 0; `bash -n scripts/smoke_test.sh` reports no syntax error; `scripts/smoke_test.ps1` again has **zero non-ASCII lines** (its section mark is
  still `[char]0x00A7`, and the new resolver is pure ASCII on purpose).
- **The two resolvers were tested as mirrors against one shared case list**, both extracted from the live scripts, 17 cases: nothing set; a real
  `MYPKI_PORT`; a file carrying host+port (with spaces around `=`), port only, or host only; `./.env` alone; `./.env` and `<config>/mypki.env`
  disagreeing; a real environment variable beating both files; the explicit flag beating everything; an invalid port in a file; an invalid port in
  the environment with a valid pair in the file; `MYPKI_CONFIG_DIR` pointing elsewhere with a quoted `export MYPKI_PORT="…"`; `MYPKI_PORT=0`; a file
  naming neither knob; and `XDG_CONFIG_HOME` empty. **The resolved URL agrees in all 17**, and the layer wording agrees in 16 — the one difference is
  case 8, where each harness names its own flag spelling (`--base/BASE` versus `-Base/$env:BASE`), which is the two languages being themselves rather
  than drift.
- **Harness baseline moves 211 → 216** (exit 0): §2 is 20 where it was 15, every other section unchanged. `SMOKE_TESTING.md`'s per-section ledger and
  *Reading the result* now carry both numbers, each attached to the build it was measured on rather than being silently rewritten.
