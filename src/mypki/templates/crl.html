What this CRL does not do

  1. It carries no IssuingDistributionPoint, on purpose. An IDP scopes a CRL to a name or a subset of certificates. Measured with openssl 3.5.6 against an IDP-scoped CRL (full_name=http://mypki.my.lab/crl.pem, only_contains_user_certs=True, critical), openssl verify -crl_check answers error 44 at 0 depth lookup: different CRL scope — for a perfectly valid leaf that carries no CDP at all, which is every certificate this CA issued before 0.7.0. The plain CRL above verifies OK. So the absence is not an omission waiting to be fixed: adding an IDP would make -crl_check unusable on this CA's own history. No delta CRLs either.
  2. Certificates issued before 0.7.0 carry no pointer. The CDP and AIA are added at signing time, so a leaf minted in 0.2.0–0.6.0 says nothing about this file and mypki cannot edit it afterwards. There is no migration and no re-issue. Those certificates can still be checked by handing the artifact to a client explicitly (openssl: -CRLfile mypki.crl.pem).
  3. openssl never fetches a CDP. Measured: with the CRL served live on a port and a leaf carrying the correct URL, openssl verify -crl_check answered error 3 at 0 depth lookup: unable to get certificate CRL and no GET ever appeared in this server's log. A baked pointer exists for clients that do fetch (browsers, Go, curl-based tooling). For openssl you must pass -CRLfile, which is what mypki's own smoke harness does.
  4. A revoked certificate that has already expired drops out of the CRL and answers UNKNOWN. Entries are rows stamped revoked and still inside their own validity, so a revoked-and-expired serial is absent from this file while its row stays in issued.db forever. There is no un-revoke and no delete. OCSP answers UNKNOWN for that serial rather than REVOKED or GOOD — the one answer that does not claim something this CRL no longer says. The CRL Number above never decreases even when entries do, because it counts stamps rather than rows in the file (RFC 5280 §5.2.1).

One more caveat stated because it changes what a client may accept: this responder is signed by the root CA itself. RFC 6960 §4.2.2.2 permits a client to accept a response signed directly by the certificate of the CA that issued the certificate being checked — that is what mypki does — but the same section also allows a client to accept only responders holding the id-kp-OCSPSigning extended key usage, and a root does not carry it. openssl 3.5 accepted this shape (measured). Whether a browser or a Go client insists on the EKU has not been tested here, so treat OCSP as the convenience and the CRL file as the artifact you can verify yourself.

What the OCSP responder does not do

  1. The request's hashes are echoed, not verified. An OCSP request names a certificate by two hashes plus a serial. This host answers with those hash values copied out of the request — it stores no certificate bytes, and it cannot recompute them for a SHA-256 request (measured). So this responder cannot prove that the request describes this CA at all. What it can prove is the answer: every status is drawn from its own record store, which is why a foreign CertID yields UNKNOWN about a serial this host does not hold rather than a statement about somebody else's certificate. Nobody but this CA's key can sign an answer here.
  2. An oversized request gets mypki's HTML error page, not OCSP bytes. Two limits sit on this route, and they are measured rather than guessed: the handler refuses any body over 8 KiB with the five-byte MALFORMED_REQUEST answer at HTTP 200, while a body above MYPKI_MAX_CSR_CHARS + 8192 — 40,192 bytes with the default knob — is answered by mypki's own HTTP 413 HTML page before any OCSP code runs. The smaller limit answers first precisely so a client that sent garbage still gets DER. No legitimate OCSP request reaches either number: real ones measure 73-101 bytes. If your client reports that the responder returned HTML, this is what happened to it.
  3. /ocsp has no CSRF token, by design. Every other POST in this app requires one, and this route is the single stated exception (page-map §0). A token proves that a page this host rendered to your browser submitted the form; an OCSP request is a machine-to-machine DER body from a client that has never seen this HTML and holds no cookie here. There is also no session state for a cross-site submit to abuse: the handler signs what its own store already says about one serial — the same fact GET /crl.pem publishes. A form-shaped POST to this URL gets the five-byte refusal and changes no record, which is asserted in mypki's tests rather than promised on this page.

How to check it yourself

curl -sSf {{ crl_base_url }}/crl.pem -o mypki.crl.pem
openssl crl -in mypki.crl.pem -noout -text          # read what it says
openssl crl -in mypki.crl.pem -noout -CAfile mypki-root-ca.crt   # verify the signature

The signature check is the point of this artifact: it is the first file mypki produces whose correctness a third party can confirm without trusting this host's word. If -CAfile reports verify failure, the file you fetched is not the one this CA signed.
