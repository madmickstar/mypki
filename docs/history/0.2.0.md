# Changelog history - [0.2.0] - 2026-10-28

Frozen record moved verbatim out of `CHANGELOG.md` when the changelog was split. **Append-only: do not restate
or re-derive these numbers.** They are measurements of the runs that produced them, and a number rewritten to
match a newer build describes a run nobody performed.

## [0.2.0] - 2026-10-28

A **MINOR** release by this file's own definition: new pages, new knobs, new fields on existing forms, and one new column
pair in `issued.db` added by an additive migration. Nothing an operator has to re-learn or re-install for — the CA on disk is
untouched, every 0.1.0 route keeps its address and its form fields, and a 0.1.0 data directory opens with no manual step.
What changed is what the pages do, not what they are called: the front page is now the signing form, the confirm step lets
names be edited, `/issued` can stamp a record revoked, and two new pages explain the host to itself.

Two things this release does **not** do, stated here because both are easy to over-read: it publishes no CRL and no OCSP
(revocations are records in this host's database, nothing a client is told), and it has no accounts (see *Known gaps* below).

### Added

- `GET /about` and `GET /settings` (page-map §12). `/about` carries the prose 0.1.0 opened its home page with, the version,
  the source URL, all three profile explanations from `signing.CERT_PROFILE_HELP`, and an explicit "what this CA does not do
  (yet)" list. `/settings` renders one row per `Settings` field — value, where it came from, and `config.py`'s own
  `Field(description=…)` sentence — built by iterating `Settings.model_fields`, so a knob added there appears without this
  file being updated in step. Both are read-only: mypki has no admin surface, and a page that could edit a limit would need
  the logins this project deliberately does not have.
- **Revocation state** on `/issued` (page-map §5): a Status column (`active` / `revoked`), a per-row Revoke control carrying
  the row's own serial, an optional reason capped at `store.MAX_REVOCATION_REASON_LENGTH` (120), and `POST /issued/revoke`.
  `issued.db` gains `revoked_at_utc` and `revocation_reason`, both NULL on a fresh row; re-revoking is a no-op that preserves
  the original stamp, because *when* the decision was made is a fact about the past. `IssuedRecord.status` is deliberately two
  states rather than three: a certificate past its `not_after_utc` still reports `active`, and printing `expired` in a column
  whose other value is `revoked` would imply this host knows what every client currently accepts.
- **Editable subject and SANs at the confirm step** (page-map §3 step B): the confirmation form's name fields start as exactly
  what the request said, an operator may change them, and every edited field goes through the same `validators.py` functions
  the generate form runs. What is *not* editable is unchanged: the public key comes only from the request, and extensions come
  only from mypki's profiles. Anything that differs from the request is named back on the issued page under "Changed from your
  request" (`_changed_subject_fields`), because an unnoticed edit is a mis-issuance this CA cannot walk back.
- **Inline form errors** (app.py "two error surfaces"): an input the operator can fix returns to the same page at HTTP 200 with
  every problem listed and every typed value still in its field, and on `/csr/sign` the staged request survives the round trip
  through `?pending=<opaque id>` in the form action — no re-paste of a 2 KB PEM. An artifact that was refused (garbage PEM, bad
  signature, CA privileges, oversized body) still goes to `error.html` at 400/403/413.
- Six subject-default knobs — `MYPKI_DEFAULT_ORGANIZATION` (`Lab`), `MYPKI_DEFAULT_ORGANIZATIONAL_UNIT` (`IT`),
  `MYPKI_DEFAULT_COUNTRY` (`AU`), `MYPKI_DEFAULT_STATE` (`Victoria`), `MYPKI_DEFAULT_LOCALITY` (`Melbourne`),
  `MYPKI_DEFAULT_EMAIL` (`it@mypki.lab`) — prefilled on the Generate-CSR page. Settings rather than constants because
  "Lab / IT / AU" is somebody else's organisation; empty leaves a field blank, and each value passes the validators the form
  applies, checked at startup (`_subject_defaults_are_valid_values`) rather than mid-signing.
- Profile help text rendered from `signing.CERT_PROFILE_HELP` on both `/csr/sign` and `/about`: what each profile is for **and
  what it will not do** — `server` is the web-server profile and does not authenticate a person, `client` proves who is
  connecting and will not make a browser trust a site, `both` is one certificate doing both jobs.
- A passphrase **floor of 8 with a recommendation of 12**, in both surfaces (`csr.PASSPHRASE_MIN_LENGTH` /
  `PASSPHRASE_RECOMMENDED_LENGTH`): the web forms and `mypki init-ca` accept 8–11 characters and say plainly that 12 or more is
  better, instead of refusing a short one or accepting it silently. The advisory names the length it saw and never the
  passphrase; `tests/test_cli.py` asserts the secret's *length* does not reach stdout/stderr when it came from
  `MYPKI_CA_PASSPHRASE`.
- A dark "strata" palette, a left-sidebar layout in the yt-dlp mould, one hand-written stylesheet and two hand-written SVG
  assets (`static/logo.svg`, `static/favicon.svg`). No JavaScript at that version and no inline styles, so the CSP stayed `default-src 'self'`
  with no `unsafe-inline` (page-map §0) — which is also why profile help is rendered for all three options at once rather than
  toggled on selection. (0.3.0 adds one same-origin script that no page requires — see the 0.3.0 entry; the CSP strings
  are unchanged, because `<script src>` is exactly what `default-src 'self'` already permits.)
- Smoke coverage for the new surface: About/Settings checks, a revoke round trip and an inline-error check in
  `scripts/smoke_test.sh` and `scripts/smoke_test.ps1`. Both harnesses now report **95 pass / 0 fail / 0 warn** against a live
  0.2.0 server — the `.sh` repeatedly on Linux, the `.ps1` once on a real Windows host (win32, Python 3.13.12, data dir
  `C:\tmp\pkismoke\data`). Their two reports were compared label by label: 95 each, same order, 86 identical, and all nine
  differences are host facts or wording rather than behaviour (SMOKE_TESTING.md, *Reading the result*).

### Changed

- `MYPKI_VALIDITY_MAX_DAYS` moves from **825 to 1461** (4 years), and over-max requests are still refused naming the limit,
  never clamped. The old ceiling existed because nothing could be revoked; with revocation *recorded*, a 2-, 3- or 4-year leaf
  becomes a defensible operator choice rather than an unbounded bet. **MEASURED on cryptography 50.0.2:** the builder accepts
  `not_valid_after` at 825, 1000, 1188, 1461 and even 3650 days without complaint — nothing in the library enforces 825, so the
  old number was this project's own policy. The widely cited 398/825-day windows are rules applied to certificates from
  publicly-trusted CAs and **could not be measured on any host here**; if a client refuses a long-lived leaf, set
  `MYPKI_VALIDITY_MAX_DAYS=825`, which is what the knob exists for.
- The sign page's provenance split replaces 0.1.0's "Only the SANs above are copied from your request", which was inaccurate:
  CN/O/OU/C/ST/L/email **do** come from the request (and from the operator's edits), and it is the *extensions* that never do.
- `/` renders the signing form with the CA facts card above it, instead of leading with prose. `/csr/sign` renders the same
  template through the same helpers, so "the front page is the sign page" is one implementation rather than two that drift.
- `store.IssuedStore` gains exactly one update method (`revoke`) and still has no delete, purge or truncate. The introspection
  test that asserted "no update, no delete" now asserts "one narrow update, no delete", and names the parameters it allows.
- Rejections an operator can fix on the confirmation page moved from error pages at 400 to inline errors at 200 — over-max
  validity, a `server` profile with no SANs, an over-cap edited SAN set, a bad country code. The sentences are unchanged; only
  where they appear is.

### Removed

- `templates/home.html`. Its prose moved verbatim to `/about`, and `/version` now renders `about.html` with the version line as
  a banner: a second page carrying the same sentences is two documents that drift. The harness contract is untouched —
  `/version` still answers 200 HTML containing `mypki <version>`.
- The claim in README, `.env.example` and page-map §5 that mypki has *no* revocation at all. It now records revocations; what
  it does not have is any way to tell a client about one.

### Fixed

- `mypki init-ca --key-type ec` never worked in any build released so far. `_ec_candidate("P-256")` formatted the
  allow-list name as `ec-256`, which is not in `keys.ALLOWED_KEY_SPECS`, so every EC root hit the policy gate and
  exited 1 on every host. The flag pair is documented as supported — `docs/page-map.md §6` lists
  `[--key-type rsa|ec] [--curve P-256|P-384]` — so an operator following this project's own spec got a refusal instead
  of a CA. Found by `tests/test_cli.py`, which is also why it survived 0.1.0: nothing else in the suite drove that flag
  pair, because every other test calls `KeySpec.from_string` with a name that is already canonical, and the broken
  translation layer had no caller to fail. Patch-level by this file's own definition (nothing an operator has to
  re-learn changes), and it does not contradict 0.1.0's *Added* bullet, which promises only "RSA-3072 / SHA-256
  self-signed root" and never claims EC support: this records a bug in a released build rather than rewriting one.

- `--secure-acl` could report success about a key it had just locked out. On a real Windows 10 host the sequence was
  measured in mypki's own log: `icacls hardening applied to <data>/ca/ca_key.pem`, and then the *same process* raised
  `PermissionError: [Errno 13] Permission denied` when it went to load that key. Narrowing a DACL can lock out the
  account that asked for it, and `_harden_with_icacls` returned True whatever `icacls` had done. It now re-opens the key
  after a successful run and returns False with a warning naming the repair (`icacls <path> /reset`) when this process
  can no longer read it, so the success line can never be printed about a CA that cannot be used. Covered by
  `tests/test_ca_init.py::test_icacls_that_locks_out_this_process_is_reported_as_failed`, which fakes the *file* rather
  than the OS: there is no portable way to make a file unreadable to its own owner (`chmod 000` works on POSIX; Windows
  `os.chmod` toggles only the read-only bit and the owner keeps reading).

- Home-directory resolution was wrong on Windows, in the product and in four tests. `Path.home()` and
  `expanduser("~")` resolve through **USERPROFILE** via ntpath there, not HOME, so a run that pinned HOME still saw
  `C:\Users\<name>\.local\share\mypki`. `src/mypki/paths.py` now resolves the home of the OS whose branch is being
  taken (`_home_for(platform_name)` / `_expand_user(path, platform_name)`, ntpath vs posixpath), which is what the
  module has always claimed to do. Tests gained the matching pins: `USERPROFILE` in `tests/conftest.py`, a
  `test_posix_branch_ignores_userprofile` mirroring the existing Windows-side test, and assertions that were silently
  asserting POSIX rules on whatever host ran them. Two tests asserted POSIX-only semantics with no gate at all and are
  now `skipif(not POSIX)`.

- Two existing `icacls` tests were wrong, and the fix above is what exposed them:
  `test_secure_acl_grants_inheritance_removal_and_full_control` and
  `test_secure_acl_falls_back_to_user_name_when_username_is_absent` both asserted a hardening success for a key file
  that did not exist. They now create it, as production does (`_harden_with_icacls` is only ever called after
  `init_ca` has written the key).

- `scripts/smoke_test.ps1` reported "NOTHING WAS CHECKED: http://127.0.0.1:8443 is not answering" against a server a
  browser reached fine. PowerShell's splat sigil takes the variable **name without `$`**, so `& curl.exe @$probeArgs`
  did not splat — it handed curl one argument starting with `@`, which curl reads as "read options from this file"
  (`curl: option @-fsS: error encountered when reading a file`, reproduced byte-for-byte on Linux). Both call sites are
  now `& curl.exe @probeArgs` / `@all`, and the probe gate separates the two failure kinds it used to collapse into one
  message: curl exit 2 is reported as *HARNESS BUG*, any other non-zero exit as a server problem naming its exit code.
  **Verified by a real PowerShell run on 2026-10-28** (a Windows host, win32 / Python 3.13.12): the harness reached its
  summary line — 95 pass, 0 fail, 0 warn — instead of dying at exit 2 with "NOTHING WAS CHECKED", which is what this bug used to
  cause. Which shell was used (`pwsh` or 5.1) is not recorded in that report. See SMOKE_TESTING.md's honesty note.

- SMOKE_TESTING.md's own setup block was a trap, and it fired on that same Windows host: it ran `mypki init-ca` with no
  data dir (so the CA went to the OS default) and then served from a *different* one
  (`MYPKI_DATA_DIR=... mypki serve`), which exits 3 `No CA found at <dir>/ca/ca_cert.pem`. Both commands now name the
  same directory, and the PowerShell spelling is given on its own line (`$env:MYPKI_DATA_DIR = "..."`) because
  `VAR=value cmd` is not valid PowerShell. README gained the matching note that `.env.example` — not `.env`, which is
  gitignored and never shipped — is the file that travels with the package.

- `mypki serve` reported the **wrong exit code** when the port was already taken, and printed none of its own message.
  The `except OSError` in `cmd_serve` looked correct and had a green test, but it never ran for the real failure:
  **measured on uvicorn 0.54.0 (`uvicorn/server.py:182-192`)**, a failed bind is logged through `uvicorn.error`, the
  lifespan is shut down, and `sys.exit(STARTUP_FAILURE)` is called -- so what arrives at mypki is `SystemExit(3)`, not
  an OSError. The operator saw uvicorn's line and exit **3**, which README documents as "required state missing: no CA
  found", sending them to look for a certificate instead of for whatever held the port. `cmd_serve` now holds the
  `Server` object, catches that `SystemExit`, checks `server.started` (False after a failed bind, True after a clean
  one -- both measured) and prints `error: cannot start <host>:<port>: the server never bound …` with exit **1**; a
  server that *did* start keeps its own exit code. Real end-to-end verification on this box: occupied port -> RC 1,
  mypki's message present, no traceback; SIGINT -> still RC 130, no message leaked. New tests
  `test_serve_reports_a_real_uvicorn_startup_failure` and
  `test_serve_does_not_rewrite_the_exit_of_a_server_that_started`; the pre-existing
  `test_serve_reports_a_bind_failure_as_exit_one_not_a_traceback` is kept but its docstring now says
  plainly that it exercises a branch real uvicorn does not feed, because its fake raises the OSError directly.

- The test suite was **not hermetic against an operator's own `.env`**, and following this project's README turned two
  green tests red. `Settings` declares `env_file=".env"`, which pydantic-settings resolves relative to the *current
  working directory*, so a `.env` in the repository root silently redefined whichever default a test was asserting:
  with `MYPKI_HOST=0.0.0.0` set (the exact edit that makes `mypki serve` reachable from a LAN),
  `test_serve_warns_in_plain_http_and_not_at_all_with_tls` demanded `https://127.0.0.1:8443` from a banner that
  correctly said `https://0.0.0.0:8443`, and the bind test demanded `cannot bind 127.0.0.1:8443` from an error naming
  `0.0.0.0`. **Reproduced on Linux** with a one-line `.env`. Fixed by an autouse fixture in `tests/conftest.py` that
  runs each test from its own empty directory (`test_packaging.py`'s "wrote nothing to disk" assertion forced that
  directory to be a *sibling* of `tmp_path`, not a child; and it must not be deleted during teardown, because
  `monkeypatch.chdir` records this fixture's directory as the cwd it restores). Mutation-checked: neutering the chdir
  makes exactly those two tests fail again. `conftest.py` 298 -> 331 lines.

- `/about` and `/version` returned **500** (`jinja2.UndefinedError`) as soon as `about.html` existed: the template renders
  `cert_profile_help`, which only `sign_context` passed, so any page that was not the sign page raised on it. Found by running
  the app and reading the response, not by reading the code — a template explaining a profile must not depend on which route
  happened to pass the mapping in, so it moved into the shared `context()`.
- Every **successful** signing POST raised `TypeError: test_none() takes 1 positional argument but 2 were given`: the issued
  card's subject row used a Jinja filter chain ending in `select('none', false)`, and Jinja read that as its built-in `none`
  test called with two arguments. Replaced with `issued.subject_display`, the string `_issued_view` already builds from the
  **finished certificate's** subject — which is the thing being displayed, where the form and the request may have differed.
- A revoke naming a serial this host has no record of answered **500** and logged at `error`: `RevocationRecordNotFoundError`
  had no handler and fell into the `MypkiError` net, so mypki described its own behaviour as broken for "that record is not in
  this database". It now answers 404 with the serial and the db file named, matching every other missing-thing answer here.
  Found by driving the route directly.

### Security

- `/settings` masks what must stay masked: `MYPKI_SECRET_KEY` renders as *set (value not displayed)* — it signs the session
  cookie that authenticates the CSRF token, so displaying it on a host with no logins would let anything that can read the page
  forge a session — and `MYPKI_SSL_KEYFILE` renders as *set (path not displayed)*. No CA or instance file path appears in the
  table at all: `paths.ca_key_path` and `paths.secret_key_path` are never consulted by `_settings_rows`, and
  `tests/test_no_key_leakage.py` proves that from outside, including the case where mypki generated the secret itself.
- `/issued`'s revoke control is CSRF-checked as the handler's first act. Without it a link on somebody else's page could flip a
  certificate to revoked with one GET-shaped request, and "revoked" is the only state change that page can cause.
- The new inline-error path never echoes a passphrase: `/csr/generate`'s re-rendered form re-renders both passphrase inputs
  empty, and the reason text names the field rather than the value.

### Known gaps in 0.2.0 (deliberate, not pending work)

**Revocations are recorded, no CRL is published.** `/issued` stamps a row and shows it; nothing signs or serves a revocation
list, and there is no OCSP responder. A certificate you revoke **stays trusted by clients until it expires** — the stamp is
evidence for the release that will build the CRL from these rows, not an effect on a client today. That is why the Revoke
button and the sentence next to it are asserted together in `tests/test_views.py` and in both smoke scripts: a page that says
"revoked" without saying what that does not do implies a capability this host does not have.

Also unchanged from 0.1.0: no ACME/SCEP/EST, no intermediate CAs, no HSM, no accounts or approval workflow, no multi-tenancy,
no JavaScript front end, no audit trail, and no delete — a record is evidence of what this CA signed, and deleting one would
make a valid certificate look never-issued.
