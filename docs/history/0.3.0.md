Frozen record moved verbatim out of `CHANGELOG.md` when the changelog was split. **Append-only: do not restate
or re-derive these numbers.** They are measurements of the runs that produced them, and a number rewritten to

## [0.3.0] - 2026-10-29

A **MINOR** release by this file's own definition: `/settings` gained the ability to write, `/issued` gained multi-select
revocation, and one new same-origin script appeared. Nothing an operator has to re-learn or re-install for — every 0.2.0
route keeps its address and its form fields, a 0.2.0 data directory opens with no manual step, and the CA on disk is
untouched. What changed is what two pages can do, plus where one page's facts live.

### Added

- **`/settings` writes `<config-dir>/mypki.env`** (page-map §12). Until now a knob could only be changed in a shell
  environment, in a `.env` next to the working directory, or with a CLI flag, and `/settings` could only *report* the
  result. The file is plain `KEY=VALUE` in the same `MYPKI_*` spelling as a shell variable, lives outside every served
  directory (`$XDG_CONFIG_HOME/mypki/`, `%APPDATA%\mypki\`), is created `0600` on POSIX, and is read at startup **below**
  real environment variables and `mypki serve` flags — so a save that seems to do nothing is a shell variable winning, and
  the page says so next to the resolved-state table.
- **Validation before the write** (`settingsfile.validate_candidate`): the candidate is built from what this process
  resolved plus what was typed, and run through `config.py` itself — every `Field(ge=…, le=…)` *and* both model
  validators. A bad save would otherwise surface as a pydantic `ValidationError` at the *next* startup: a CA that refuses
  to boot because of something typed into a text box an hour earlier. Refusals name the knob and the bound from the same
  `Ge`/`Le` objects pydantic enforces, so the page's promise and `config.py`'s rule cannot drift; a rejected save leaves
  the file byte-identical.
- **`MYPKI_LOG_LEVEL` is checked before it is written**, through `logsetup.resolve_level` — the function that would
  otherwise fail at startup an hour later. It is the one editable knob `config.py` does not validate itself, its type being
  plain `str`.
- **Four answers for an empty text box**, one per kind of knob, each from measurement rather than assumption:
  `log_file` and the six subject defaults write an empty line (MEASURED to read back as `None`, which is what those fields
  document — "console only", "no prefilled organisation"); `data_dir` and `public_base_url` write no line at all, because
  MEASURED `MYPKI_DATA_DIR=` reads back as `PosixPath('.')` and would put a root CA's private key in whatever directory
  the service happened to be standing in; `host`, `ca_cn` and `log_level` are refused naming the knob, because an empty
  line there survives into the running process (`MYPKI_HOST=` yields `''`, and `cli._is_loopback('')` is False).
- **`secret_key`, `ssl_certfile`, `ssl_keyfile` and `config_dir` are not editable** (`settingsfile.UNMANAGED_KEYS`), each
  with its reason stated on the page. A session-signing secret sent through a form appears in a POST body, in whatever
  logged that body, and in a browser history; `config_dir` is where this file lives, so the file cannot carry it. A line an
  operator hand-wrote for any of them is preserved byte-for-byte by Save (`preserve_unmanaged`) — silently dropping a line
  nobody asked to drop is how a settings page becomes dangerous.
- **Multi-select revocation on `/issued`** (page-map §5): every active row carries a `serial_hex` checkbox inside one bulk
  form, the Select column offers an All box, and **Revoke Selected** submits N serials at once. Blank selection answers 400
  naming `serial_hex`; duplicates collapse so select-all plus a hand-ticked row is one revocation, not two; values are
  stripped and lowercased because `store.revoke` addresses rows by the lowercase hex it wrote.
- **A server-side confirmation step**: a POST without `confirm=1` stamps nothing and returns the page naming every
  certificate about to be stamped — serial *and* common name — plus what this host already knows about each one (`active
  now`, `already revoked — its stamp and reason will not change`, `not a record on this host`). The confirm form carries the
  same N serials forward as hidden fields, so "confirmed" cannot mean a different batch than the one shown.
- **A three-way batch report**: `N stamped now / N already revoked before this submit / N with no record on this host`, each
  serial named under its own outcome. `store.revoke()` answers None for a serial this host never signed and returns the
  untouched record for an already-stamped one, so a batch can legitimately mix all three, and reporting them as one number
  would hide the case an operator most needs told about — a stale tab selecting a certificate somebody else already revoked.
- **`static/app.js`**, one same-origin script (11 KB, hand-written, no build step, no dependency): copy-to-clipboard for PEM
  blocks, the select-all box and live "N selected" counter on `/issued`, and a revoke modal whose Confirm adds `confirm=1`
  to the same form the server-rendered confirmation block represents. **No page requires it**: with JavaScript off every
  page above works, the All box stays an inert checkbox, and ticking rows by hand reaches the identical POST. It is loaded
  with `<script src>`, which `default-src 'self'` already permits — no `unsafe-inline`, no CDN, and CSP strings unchanged.

### Changed

- **The CA facts card moved off `/` onto `/ca`, and is on `/ca` only.** Subject, serial, validity window, colon-grouped
  SHA-256 fingerprint, key type/size, `CA:TRUE pathLength:0` and private-key presence were rendered on three pages; a fact
  shown in two places is two facts that can disagree. `home()` still renders the same `sign_page()` as `/csr/sign`, so "the
  front page is the sign form" remains one implementation. Both smoke harnesses' §1 CA assertions moved to `/ca` with it,
  and `tests/test_views.py`'s two CA tests were re-pointed rather than deleted — the assertion did not weaken, it moved to
  the single page that now has to carry it.
- **`app._form_fields_multi`**, a second form dependency for bodies where one field legitimately appears N times: MEASURED
  on starlette 1.10, `FormData.items()` yields only the *last* value of a repeated key, so three ticked boxes would silently
  collapse into one revoke. Every other handler keeps the single-value shape rather than carrying `[0]` subscripts.
- **A single unknown serial still answers 404** naming both the serial and the database file (0.2.0's measured contract),
  while a batch of two or more carries on to the three-way report. Where the line is drawn is itself asserted as a pair of
  tests: a hand-pasted serial from another machine's CA is one certificate, and answering it with a 200 batch card would
  say "nothing was changed" in the same shape as "the submit worked"; 404-ing N-1 decisions the operator did mean to make
  is the larger error.

### Fixed

- **`/settings` answered 500 on a config directory it could not write.** `except OSError` sat on the
  `validate_candidate` try, which performs no I/O at all, so the handler this function's own docstring promised ("named
  plainly, with the path, rather than rendered as a 500") was unreachable and `<config>/mypki` existing as a *file* produced
  a traceback. The handler now sits on `write_settings_file`, which is what touches the filesystem. Found by
  `tests/test_settings_save.py`, not by reading the code.
- **`validate_candidate` contradicted its own docstring on three knobs.** An empty `log_file` box dropped the line instead
  of writing it, so "console only" silently reverted to `logs/mypki.log`; an empty subject default dropped its line for the
  same reason, restoring mypki's `Lab / IT / AU` behind an operator who had just asked for no prefilled organisation; and
  `host`, `ca_cn` and `log_level` accepted an empty value that this module's comment claimed it would refuse. All four are
  now the behaviour the docstring describes, with the measurements that decide each branch written into it.
- **A choice knob could have written the word `None`.** `MYPKI_LOG_FILE=None` reads back as `PosixPath('None')` — a log
  file actually named None (MEASURED) — which is the same class of bug `config.py`'s `_empty_log_file_means_console_only`
  exists to prevent, approached from the writing side. Empty is now rendered as an empty line.
- **`settingsfile.py` emitted a `SyntaxWarning: invalid escape sequence '\m'` on every import** (its module docstring
  spelled `%APPDATA%\mypki`). It printed twice in every pytest run; the backslashes are doubled, which renders identical
  text with no warning.

### Security

- Nothing this page can write is a credential or a path to one: `secret_key` and both `ssl_*` paths stay masked *and*
  non-editable, and `tests/test_no_key_leakage.py` now asserts their absence twice — absent as text, and absent as a
  submittable control (`name="MYPKI_SECRET_KEY"` and friends). `tests/test_settings_save.py` asserts the
  editable/unmanaged split is exhaustive over `Settings.model_fields`, so a knob added to `config.py` cannot become a text
  box silently.
- The saved file is created with mode `0600` rather than written and then chmodded, so there is no window where it is
  world-readable — the same reasoning `ca.PRIVATE_FILE_MODE` uses for a private key. Asserted on POSIX as
  `stat.S_IMODE(mode) & 0o077 == 0`.

### Testing

- **`scripts/smoke_test.sh` was rewritten for this build and run green: `== summary: 156 pass, 0 fail, 0 warn ==`** (exit 0)
  against a live 0.3.0 server on Linux 2026-10-29 (`http://127.0.0.1:8443`, `MYPKI_DATA_DIR=/tmp/pkismoke/data`, CA loaded,
  console-only logging). §1's four CA assertions moved to `/ca` and were **inverted on `/`** into absence checks — a home page
  that grew the CA card back would still answer 200 and every other §1 check would still pass. §2 now asserts `app.js` is served,
  linked with `<script src>`, typed `text/javascript`, carries the same CSP, and that no page inlines a script. §10 counts
  checkboxes against active rows and asserts ONE bulk form. §11 became a five-step walk: unconfirmed → confirmed → three-serial
  multi-select → mixed batch → re-submit of an already-stamped serial. §12 fingerprints the config file (`absent` is a real
  state) and compares that fingerprint across three refused saves.
- **The pre-edit harness, run unchanged against this same 0.3.0 app, printed `88 pass, 7 fail, 0 warn` (exit 1).** All seven were
  the harness being wrong rather than the app: §1's four CA needles aimed at `/`, and §11's three asserted a confirmation block
  that did not exist yet plus a control-count fall that one bulk form makes impossible (MEASURED as 1 -> 2). That baseline is
  recorded because it is the evidence that the rewritten sections test something.
- Two harness assertions were corrected **from measurement before they were trusted**. "An unconfirmed POST shows zero revoked
  pills" fails against a correct app on a ledger that already holds revoked records (MEASURED: 6 legitimately present) — the real
  contract is that the count does not move. And a body with a knob *deleted* would have **written the operator's real config
  file**, because `_submitted_settings_fields` fills absent knobs rather than refusing them; the refusal posted instead is an
  empty `MYPKI_HOST=`. The batch card's apostrophe was checked byte for byte: `this host's database` is plain ASCII U+0027, so
  asserting `&#8217;` would have failed against a correct page.
- **`scripts/smoke_test.ps1` mirrors every label** (same fourteen headings, same per-section counts, LF-only, zero non-ASCII
  bytes) and **has not been run from this build.** No Windows number is claimed for 0.3.0; the 95/0/0 figures elsewhere in this
  file describe the 0.2.0-era tree.

### Known gaps in 0.3.0 (deliberate, not pending work)

- **Revoking still publishes nothing.** No CRL, no OCSP responder, no delete: a stamp is a row in `issued.db` on this host,
  and a client that already trusts the certificate keeps trusting it until it expires. The sentence is rendered next to the
  button, in the confirmation block, in the batch report and in the table footer, and both harnesses fail the run if it is
  missing from any of them.
- **`/settings` changes what the *next* start reads**, not what this process is doing. `MYPKI_HOST`, `MYPKI_PORT`,
  `MYPKI_SESSION_MAX_AGE` and the logging knobs are read once at startup; the page says which ones, per save.
- **The script's clipboard path was never observed in a browser on the Linux host these notes were written on** (none is
  installed). `navigator.clipboard` needs a secure context, so on plain HTTP it falls back to `execCommand('copy')` and the
  page keeps offering Download; what both harnesses assert is that `app.js` is served and linked, not that a copy worked.
- **`scripts/smoke_test.ps1` has not been run from this build**; see SMOKE_TESTING.md for which numbers are measured on
  which host.
